# Requirements Document

## Introduction

The Agent-Friendly Resume feature synthesizes a user's REGAIN platform data — profile, campaign progress, completed missions, evidence vault entries, and market alignment — into a structured markdown resume with machine-readable YAML frontmatter. The resume is generated by the LLM (Nova Lite) from real evidence, not from templates. It serves two audiences: human recruiters reading the prose body, and AI recruiting agents parsing the YAML frontmatter to score candidates programmatically. The resume regenerates automatically on mission completion and phase advancement, and is accessible via API endpoints and a dedicated frontend page.

## Glossary

- **Resume_Generator**: The backend service (Lambda function) that gathers data from all DynamoDB tables, invokes Nova Lite to synthesize the resume, and stores the result in S3.
- **Resume_Document**: The output markdown file containing YAML frontmatter (machine-readable metadata) and a markdown body (human-readable prose sections).
- **Frontmatter**: The YAML block at the top of the Resume_Document delimited by `---` markers, containing structured fields parseable by AI recruiting agents.
- **Resume_Bucket**: The S3 bucket (or prefix within an existing bucket) where Resume_Documents are stored, organized by user ID.
- **Coaching_Agent**: The existing Strands SDK agent with @tool-decorated functions that provides adaptive coaching to users.
- **Resume_API**: The API Gateway endpoints (GET /resume, POST /resume/generate) that serve resume data to the frontend.
- **Resume_Page**: The frontend React page that renders the Resume_Document and provides download and regeneration controls.
- **Evidence_Vault**: The DynamoDB table storing tagged skill evidence from completed missions.
- **Mission_Engine**: The existing backend module that handles mission lifecycle, difficulty adjustment, and phase gate evaluation.
- **Market_Alignment**: The percentage score (0-100) representing how well a user's demonstrated skills match their target role's market requirements.

## Requirements

### Requirement 1: Resume Document Schema

**User Story:** As an AI recruiting agent, I want to parse a candidate's resume frontmatter as structured YAML, so that I can programmatically score the candidate against a job description without reading prose.

#### Acceptance Criteria

1. THE Resume_Document SHALL contain YAML frontmatter delimited by `---` markers as the first content in the file, followed by a markdown body.
2. THE Frontmatter SHALL include the following fields: schema_version (string), generated_at (ISO 8601 timestamp), regain_version (string), name (string), target_role (string), transition_type (string), skills (array of objects), campaign_phase (string), campaign_progress_pct (number), market_alignment_score (number), missions_completed (number), evidence_items (number), and top_accomplishments (array of strings).
3. WHEN a skill object is included in the Frontmatter skills array, THE skill object SHALL contain: skill_name (string), evidence_count (number), strongest_evidence_summary (string), and proficiency_indicator (string derived from evidence depth).
4. THE Frontmatter SHALL exclude personally identifiable information beyond name and target_role — no email, phone number, or physical address.
5. THE Resume_Document markdown body SHALL contain five sections in order: Professional Summary, Skills and Demonstrated Capabilities, Campaign Progress, Mission History Highlights, and Market Alignment.
6. FOR ALL valid Resume_Documents, parsing the YAML frontmatter then serializing it back to YAML then parsing again SHALL produce an equivalent object (round-trip property).

### Requirement 2: LLM-Synthesized Resume Content

**User Story:** As a career transitioner, I want my resume to read as a professionally written narrative backed by my documented evidence, so that it reflects my actual demonstrated capabilities rather than generic filler.

#### Acceptance Criteria

1. WHEN the Resume_Generator synthesizes the Professional Summary section, THE Resume_Generator SHALL produce 2-3 sentences written by Nova Lite based on the user's background, trajectory, and documented growth — not from a template with string interpolation.
2. WHEN the Resume_Generator synthesizes the Skills and Demonstrated Capabilities section, THE Resume_Generator SHALL list each skill with evidence-backed bullet points that reference specific mission titles, completion dates, and evidence reflections.
3. WHEN the Resume_Generator synthesizes the Mission History Highlights section, THE Resume_Generator SHALL include 5-8 completed missions curated by Nova Lite for relevance to the user's target role, each with a reflection excerpt.
4. WHEN the Resume_Generator selects top_accomplishments for the Frontmatter, THE Resume_Generator SHALL select 3-5 achievements based on impact and relevance to the target role, each backed by at least one Evidence_Vault entry.
5. THE Resume_Generator SHALL determine proficiency_indicator values for each skill based on evidence depth (number of evidence entries and quality of reflections), not from user self-assessment.
6. WHEN the Resume_Generator synthesizes the Market Alignment section, THE Resume_Generator SHALL include the target role, alignment percentage, demonstrated in-demand skills, and active skill gaps the user is working on.

### Requirement 3: Resume Data Gathering

**User Story:** As a platform operator, I want the resume generation service to gather all relevant user data from existing tables in parallel, so that resume generation completes within acceptable latency.

#### Acceptance Criteria

1. WHEN the Resume_Generator is invoked, THE Resume_Generator SHALL read the user profile from the UserProfiles table, the active campaign from the Campaigns table, all completed missions from the MissionHistory table, all evidence entries from the Evidence_Vault table, and market alignment data from the MarketData table.
2. WHEN the Resume_Generator gathers data, THE Resume_Generator SHALL execute DynamoDB queries in parallel to minimize total latency.
3. WHEN the Resume_Generator calculates Market_Alignment, THE Resume_Generator SHALL invoke the same alignment calculation logic used by the get_alignment Coaching_Agent tool.
4. IF any DynamoDB query fails during data gathering, THEN THE Resume_Generator SHALL return an error response with the specific table that failed, without generating a partial resume.
5. WHEN the Resume_Generator is invoked for a user with zero completed missions, THE Resume_Generator SHALL return an error indicating that at least one completed mission is required before resume generation.

### Requirement 4: Resume Storage

**User Story:** As a user, I want my resume history preserved automatically so that I can see how my professional narrative has evolved over my campaign.

#### Acceptance Criteria

1. WHEN the Resume_Generator produces a Resume_Document, THE Resume_Generator SHALL store the document in the Resume_Bucket at the path `{userId}/resume/resume-{ISO 8601 timestamp}.md`.
2. WHEN the Resume_Generator produces a Resume_Document, THE Resume_Generator SHALL overwrite the file at `{userId}/resume/latest.md` with the new content.
3. WHEN the Resume_Generator stores a Resume_Document, THE Resume_Generator SHALL update the UserProfiles table with lastResumeGeneratedAt (ISO 8601 timestamp), resumeS3Key (S3 object key for latest.md), and resumeVersion (incrementing integer).
4. THE Resume_Bucket SHALL have S3 versioning enabled to preserve the history of the latest.md object.
5. THE Resume_Bucket SHALL block all public access.

### Requirement 5: Mission Completion Trigger

**User Story:** As a user, I want my resume to automatically incorporate my latest mission evidence without me having to remember to regenerate it.

#### Acceptance Criteria

1. WHEN the complete_mission tool in the Coaching_Agent successfully completes a mission, THE system SHALL invoke the Resume_Generator asynchronously for that user.
2. WHEN the Resume_Generator is triggered by mission completion, THE Resume_Generator SHALL execute without blocking the mission completion response to the user.
3. IF the asynchronous resume generation invocation fails, THEN THE system SHALL log the failure without affecting the mission completion result.

### Requirement 6: Phase Advancement Trigger

**User Story:** As a user advancing to a new campaign phase, I want my resume narrative restructured to reflect my new phase and updated accomplishments.

#### Acceptance Criteria

1. WHEN a campaign transitions from one phase to the next (Foundation to Expansion, or Expansion to Launch), THE system SHALL invoke the Resume_Generator asynchronously for that user.
2. WHEN the Resume_Generator is triggered by phase advancement, THE Resume_Generator SHALL produce a Professional Summary that reflects the user's new campaign phase.
3. THE system SHALL invoke the Resume_Generator only on mission completion and phase advancement events — not on profile edits, coaching conversations, evidence-only logs, or login events.

### Requirement 7: Coaching Agent Resume Tools

**User Story:** As a user in a coaching session, I want to ask my coach about my resume and have it generated or retrieved on demand during our conversation.

#### Acceptance Criteria

1. THE Coaching_Agent SHALL provide a generate_resume tool that invokes the Resume_Generator and returns the S3 presigned URL for the generated Resume_Document.
2. THE Coaching_Agent SHALL provide a get_resume tool that returns the latest Resume_Document content (markdown string) and metadata (version, generated_at, S3 presigned URL) without triggering regeneration.
3. WHEN the generate_resume tool is invoked, THE generate_resume tool SHALL return the presigned URL, resume version, and generated_at timestamp.
4. WHEN the get_resume tool is invoked for a user with no existing resume, THE get_resume tool SHALL return a message indicating no resume exists yet.
5. THE generate_resume and get_resume tools SHALL follow the existing @tool decorator pattern used by the Coaching_Agent's other tools.

### Requirement 8: Resume API Endpoints

**User Story:** As a frontend developer, I want REST API endpoints to retrieve and regenerate the resume, so that the Resume_Page can display current resume data.

#### Acceptance Criteria

1. THE Resume_API SHALL expose a GET /resume endpoint that returns the resume markdown content, generated_at timestamp, version number, and a presigned S3 download URL with 1-hour expiry.
2. WHEN GET /resume is called for a user with no existing resume, THE Resume_API SHALL return HTTP 404 with the message "Complete your first mission to generate your resume".
3. THE Resume_API SHALL expose a POST /resume/generate endpoint that triggers on-demand resume generation and returns the same response shape as GET /resume with freshly generated content.
4. THE Resume_API SHALL enforce a rate limit of 3 manual generations per user per day on the POST /resume/generate endpoint.
5. WHEN the rate limit is exceeded on POST /resume/generate, THE Resume_API SHALL return HTTP 429 with a message indicating the daily generation limit has been reached.
6. THE Resume_API SHALL require Cognito authorization on both endpoints, consistent with all other REGAIN API endpoints.

### Requirement 9: Resume Frontend Page

**User Story:** As a user, I want a dedicated page in the REGAIN app where I can view, download, and regenerate my resume.

#### Acceptance Criteria

1. THE Resume_Page SHALL be accessible as a new navigation item in the sidebar, positioned between Evidence and Profile.
2. THE Resume_Page SHALL render the Resume_Document markdown body using the same markdown rendering approach used on the Coaching page.
3. THE Resume_Page SHALL display the Frontmatter fields as structured metadata above the rendered markdown body — not as raw YAML.
4. THE Resume_Page SHALL provide a "Download .md" button that downloads the raw Resume_Document markdown file.
5. THE Resume_Page SHALL provide a "Regenerate" button that calls POST /resume/generate and displays the updated resume upon completion.
6. THE Resume_Page SHALL display a version indicator showing the resume version number and time since last generation (e.g., "Version 7 — Generated 2 hours ago").
7. WHEN the user has no existing resume, THE Resume_Page SHALL display a message indicating that completing a first mission is required to generate a resume.
8. WHILE the Resume_Page is loading resume data, THE Resume_Page SHALL display a loading indicator.
9. WHILE resume regeneration is in progress, THE Resume_Page SHALL disable the Regenerate button and display a progress indicator.

### Requirement 10: Resume CDK Infrastructure

**User Story:** As a platform operator, I want the resume infrastructure provisioned via CDK with least-privilege IAM, so that the feature integrates cleanly with the existing stack architecture.

#### Acceptance Criteria

1. THE CDK infrastructure SHALL provision a Resume_Bucket (or configure a dedicated prefix on an existing bucket) with S3 versioning enabled and public access blocked.
2. THE CDK infrastructure SHALL provision a Resume Generation Lambda with read permissions on all five DynamoDB tables, write permissions to the Resume_Bucket, and Bedrock invoke permissions for Nova Lite.
3. THE CDK infrastructure SHALL add GET /resume and POST /resume/generate routes to the existing API Gateway with Cognito authorization.
4. THE CDK infrastructure SHALL follow the existing pattern of one stack per service domain, using CfnOutput and Fn.importValue for cross-stack references.
5. THE CDK infrastructure SHALL tag all new resources with Project=REGAIN and Environment=dev.
6. THE Resume Generation Lambda SHALL have IAM permissions scoped to only the specific resources it needs (least privilege).

### Requirement 11: Resume Generation Performance and Validity

**User Story:** As a user, I want my resume generated quickly and formatted correctly every time, so that I can trust the output.

#### Acceptance Criteria

1. THE Resume_Generator SHALL complete resume generation (data gathering, LLM synthesis, S3 storage) within 15 seconds.
2. THE Resume_Generator SHALL produce output that is valid markdown parseable by any standard markdown renderer.
3. THE Resume_Generator SHALL produce YAML frontmatter that is valid YAML parseable by any standard YAML parser.
4. THE Resume_Generator SHALL not include raw DynamoDB keys, evidence IDs, or internal system identifiers in the Resume_Document.
5. THE Resume_API SHALL generate S3 presigned URLs with a 1-hour expiry, and the frontend SHALL request a fresh URL on each page load.
